Diagnostico de conectividad (correccion final):
- El diagnostico temporal dentro del mismo runtime `workerd` confirmo:
  `binding.otariApiKeyPresent=true`; `https://example.com` devolvio HTTP 200;
  `https://api.otari.ai/api/v1/health` devolvio HTTP 403; y `/models`
  devolvio HTTP 403 con `content-type=text/html` y `server=awselb/2.0`.
- Se probaron tres formas de autenticacion sin registrar valores:
  `Otari-Key`, `Authorization` y `Authorization: Bearer`. Las tres recibieron
  HTTP 403 desde el runtime Worker. Esto descarta DNS, conexion TLS y timeout;
  el rechazo ocurre en la fase HTTP upstream. El binding si llega al Worker.
- La causa inmediata del `transport_error` era un bug de clasificacion local:
  `listOtariModels` intentaba ejecutar `response.json()` antes de comprobar
  `response.ok`. El upstream devolvia HTML 403, el parseo lanzaba
  `SyntaxError` y el catch lo convertia en `transport_error`.
- Se corrigio el orden: ahora un rechazo HTTP devuelve `status=403` y
  `code=http_403`, sin intentar parsear el cuerpo ni exponerlo. La causa
  residual del 403 parece especifica del egress/runtime o de la politica
  upstream, no del binding ni de la URL; no se afirma mas sin evidencia del
  proveedor.
- El endpoint temporal de diagnostico fue eliminado antes del commit final;
  no queda una ruta que pruebe cabeceras ni presencia del secreto.
